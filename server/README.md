# Phoenix_Bolotni — серверный распознаватель птиц и карта активности

Принимает непрерывный поток аудио от микрофонов и телефонов, распознаёт виды
**многократной проверкой** (скользящие окна + голосование, см. `confirmation.py`)
и строит по накопленным детекциям **зоны активности видов на карте**.

Ключевое ограничение, которому подчинён весь остальной код: **аудио не сохраняется
нигде** — ни на диске, ни в БД, ни в очереди. Байты принятого чанка живут в
оперативной памяти процесса и освобождаются сразу после инференса. В БД попадают
только числа: вид, уверенность, время, координаты.

---

## Что публично, а что живёт только за VPN

Это требование заказчика (td3.md, раздел 2), и оно определяет, где что должно
стоять. Сотни полевых микрофонов должны достучаться по обычному HTTP, поэтому
закрыть всё VPN-доступом нельзя: тогда запись в поле работать не будет.

| Часть | Доступ | Почему |
|---|---|---|
| `POST /ingest` (приём чанков) | **Публичный HTTPS** | Микрофоны в поле шлют данные сами, VPN у них нет |
| Регистрация устройств | Только изнутри (VPN/туннель) | Кто угодно иначе заведёт фантомный микрофон |
| API карты и дашборд | Только изнутри (VPN/туннель) | Данные мониторинга редких видов; в комментарии к `PHOENIX_DASHBOARD_PASSWORD` названы последствия утечки |
| БД (Postgres+PostGIS) | Только изнутри | Токены устройств, история наблюдений |
| Модель и код | Только изнутри | — |

Рекомендуемая раскладка (та же, что в td3.md, раздел 2):

```
микрофоны ──HTTPS──▶ тонкий публичный релей ──VPN/туннель──▶ сервер за VPN
   (поле)             (дешёвый VPS, только приём              (инференс, БД,
                       и отдача 202 Accepted)                  карта, дашборд)
```

**Важное отступление от исходной схемы.** td3.md предлагает, чтобы релей принимал
файлы и «пересылал задания» по приватному каналу, а очередь была VPN-only. Здесь
реализовано иначе: рель и обработка живут в **одном процессе**, потому что байты
аудио нельзя передать — они и должны умереть в том же процессе, который их принял.
Переслать аудио по сети — значит записать его на диск или в БД на промежуточном
узле, а это ровно то, что запрещено.

Отсюда следствие: если инференс не успевает, очередь переполняется и `/ingest`
честно отвечает `503`, а устройство повторяет загрузку. Обмен «стабильная
пропускная способность ценой памяти» на «честная перегрузка ценой потери части
записей» — сознательный выбор под требование не сохранять аудио.

Если понадобится разделить приём и обработку, выносить надо **очередь заданий**
(метаданные, без байтов), а не аудио.

## Быстрый старт

```bash
cd server
cp .env.example .env          # секреты заменить; для локального запуска см. ниже
docker compose up --build
```

Дашборд: <http://localhost:8000/>. API приёма: `POST /ingest`.

Зарегистрировать микрофон и получить токен (внутри контейнера):

```bash
docker compose exec api python -m server.cli device add \
    --name "Пойма у моста" --lat 59.90 --lon 41.10 --owner "Иван"
```

Для локального запуска без HTTPS:

```bash
# в .env
PHOENIX_DASHBOARD_AUTH=false
POSTGRES_PASSWORD=любой_пароль_для_локалки
```

### Без контейнеров (разработка и тесты)

```bash
pip install -r requirements.txt -r server/requirements.txt
export PHOENIX_DATABASE_URL="sqlite:///./server/data/phoenix.db"
export PHOENIX_DASHBOARD_AUTH=false
export PHOENIX_INLINE_WORKER=true

python -m server.cli device add --name "Пойма" --lat 59.90 --lon 41.10
uvicorn server.ingest:app --reload
```

Тесты:

```bash
python -m pytest server/tests/ -q
```

Тесты идут на SQLite и не требуют ни Postgres, ни ONNX-модели: анализатор
подменяется заглушкой. Отдельно проверяется, что схема из миграций совпадает со
схемой из моделей — расхождение ловится до деплоя, а не на нём.

## Устройство

```
server/
  confirmation.py   многократная проверка: окна 5.0 с / шаг 2.5 с, TTA ±200 мс,
                    голосование M=3, K=2, порог 0.6 (всё из model_config.json)
  ingest.py         FastAPI: публичный рель /ingest + встроенный воркер
  queue_worker.py   инференс → дедупликация → запись подтверждённых детекций
  spool.py          очередь байтов в RAM: лимит по объёму + TTL, переполнение → 503
  dedup.py          детекция на стыке перекрывающихся чанков не пишется дважды
  devices.py        реестр: токены (только SHA-256), статусы, heartbeat
  api_devices.py    административный API реестра (за VPN)
  api_map.py        API карты активности + экспорт CSV/GeoJSON
  zones.py          зоны активности: сетка, KDE, полигоны покрытия, сравнение периодов
  geohash.py        разбиение карты на ячейки (размер считается из числа битов)
  geo.py            геопримитивы без PostGIS (работают и на SQLite)
  analytics.py      выборки детекций; на Postgres радиус идёт через ST_DWithin
  models.py         схема БД; `lat/lon` — источник правды, `geom` — для индекса
  auth.py           Bearer-токены устройств и Basic-аутентификация дашборда
  cli.py            регистрация устройств, разрывы, миграции, сводка
  alembic/          миграции (в проде схема создаётся только ими)
  webapp_map/       дашборд Leaflet
```

### Модель подключается как внешняя библиотека

Репозиторий модели не копируется в `server/`. Используются его файлы как есть:
`model_config.json`, `species/ru_birds_whitelist.json`, `models/classes.json`,
`models/bird_model.onnx` и модуль `inference.py`. Пути настраиваются
переменными `PHOENIX_MODEL`, `PHOENIX_CLASSES`, `PHOENIX_MODEL_CONFIG`,
`PHOENIX_WHITELIST`.

В docker-compose репозиторий модели подключается **томом на чтение**, а не
`COPY`: `models/bird_model.onnx` в git хранится указателем git-LFS, и копирование
в образ дало бы 133-байтный файл-заглушку. Путь задаётся `MODEL_REPO_PATH`.

В whitelist 136 видов, модель распознаёт 16. `/api/map/species` отдаёт весь
whitelist с флагом `in_model`: экологу нужен справочник фауны площадки, а не
только то, что модель уже умеет.

## Схема данных и почему в ней нет аудио

Таблицы создаются миграциями (`server/alembic/versions/`), а не `create_all` — иначе
PostGIS-геометрия, GiST-индекс и триггер синхронизации `lat/lon` → `geom` остались
бы вне контроля версий.

| Таблица | Что хранит |
|---|---|
| `devices` | Реестр микрофонов: координаты, хеш токена, heartbeat |
| `chunks` | Метаданные загрузок: время, длительность, перекрытие, разрыв, `sha256` |
| `jobs` | Очередь обработки: статусы, попытки, счётчики |
| `detections` | Подтверждённые детекции: вид, уверенность, окно, координаты, `geom` |
| `device_events` | Разрывы связи, деактивации |
| `raw_windows` | Отладочные per-window предсказания (только числа, выключено по умолчанию) |

Аудио-колонок и аудио-таблиц нет вообще. Токены устройств хранятся только как
SHA-256-хеш: украденная копия БД не даёт возможности заливать данные от чужого
микрофона. Сам токен показывается один раз — при регистрации и при выпуске нового.

`lat`/`lon` в `detections` — источник правды. `geom geometry(Point, 4326)` — для
PostGIS и радиусных выборок: без него `ST_DWithin` сканирует таблицу целиком.
Значение синхронизируется триггером `trg_detections_sync_geom` в БД (ORM-хук не
ловит правки из `psql`/`COPY`).

На SQLite геометрия хранится текстом, а вся аналитика считается в Python
(`geo.py`, `zones.py`) — поэтому тесты не требуют PostGIS.

### Миграции

В проде схему создаёт **только** `alembic upgrade head`, и он же вызывается при
старте процесса (`init_db` в `db.py`). На SQLite (разработка и тесты) `init_db`
по-прежнему создаёт таблицы из моделей: гонять миграции при каждом запуске
тестов неудобно, а их актуальность проверяется в `test_migrations.py`.

```bash
python -m server.cli db upgrade      # применить
python -m server.cli db check        # сверить миграции с моделями (можно в CI)
python -m server.cli db current      # текущая ревизия
python -m server.cli db downgrade -1 # откатить на шаг
```

Гонки при одновременном старте контейнеров сняты advisory-блокировкой Postgres.
`db check` — главная проверка релиза: расхождение миграций и моделей означает,
что на следующем `upgrade` в проде что-то не совпадёт с кодом.

## Чего этот стек не умеет

Здесь перечислено то, что выглядит как пробел, но на самом деле следствие
выбранных требований. Если понадобится иначе — менять придётся именно эти места.

**Redis в стеке нет.** В исходном ТЗ он предполагался как очередь. Здесь очередь
живёт в памяти процесса, потому что Redis — это дисковое хранилище: положенные в
него байты переживут перезапуск, попадут в бэкап и окажутся на месте, где их никто
не ждёт. Для аудио это неприемлемо. Когда появится реальная потребность в общей
очереди, выносить следует **задания** (метаданные, без байтов) — Redis для этого
подходит.

**Воркер один и живёт внутри процесса API** (`PHOENIX_INLINE_WORKER=true`).
Отдельный контейнер воркера увидит задание в БД, но байтов в своей памяти не
найдёт и пометит его `expired` — тихая потеря наблюдения. Это зафиксировано
тестом `test_separate_worker_process_would_expire_jobs`. Масштабирование требует
сначала вынести очередь в общее хранилище, и только потом отключать эту опцию.

**Горизонтального масштабирования приёма нет.** Один процесс = одна копия spool в
памяти. Потолок пропускной способности — `PHOENIX_SPOOL_MAX_BYTES` и скорость
инференса на CPU. При переполнении честный `503`.

**TLS терминируется снаружи.** Контейнер слушает HTTP на `127.0.0.1:8000`;
сертификат и публичный адрес — задача релея или nginx перед ним.

**Время в UTC.** Час суток в фильтрах карты (`hours`) — всегда UTC, иначе
срез «когда активен вид» зависел бы от часового пояса запроса.

**`raw_windows` и отладочное аудио выключены по умолчанию.** `PHOENIX_STORE_RAW_WINDOWS`
заполняет таблицу примерно с потоком детекций; `PHOENIX_DEBUG_KEEP_AUDIO` — единственная
настройка, при которой байты попадают на диск, и она включается только на время
разбора одного инцидента (плюс TTL и лимит на число файлов).

**Модель в этом репозитории недоступна.** `models/bird_model.onnx` — указатель
git-LFS (133 байта). Тесты используют заглушку анализатора; реальный инференс
проверить можно только после `git lfs pull`.

## Операции

```bash
python -m server.cli status                 # очередь, память, устройства
python -m server.cli summary --days 7       # своды по видам, пики активности
python -m server.cli gaps                   # кто молчит и с какого разрыва
python -m server.cli sweep                  # разово зафиксировать разрывы (cron)
python -m server.cli species                # справочник: 136 видов, 16 классов
python -m server.cli worker --once          # разовая обработка очереди
python -m server.cli device list            # состояние всех микрофонов
```

### Алерты о разрывах связи

`server/alerts` считает молчание дольше `PHOENIX_GAP_ALERT_SEC` и пишет в
`PHOENIX_ALERT_LOG` и/или `PHOENIX_ALERT_WEBHOOK`. В compose это отдельный сервис:
он не держит модель в памяти, но нужен постоянно — упавший вместе с API мониторинг
означал бы, что о пропавших микрофонах никто не узнает.

Устройство, которое ещё ни разу не прислало чанк, разрывом **не** считается
(состояние `never_seen`) — иначе каждое только что зарегистрированное устройство
 немедленно попадало бы в алерты. Молчание само по себе поводом для
деактивации не является: это сигнал оператору, а не приговор.

### API карты

| Метод и путь | Назначение |
|---|---|
| `GET /api/map/species` | Справочник видов с флагом `in_model` |
| `GET /api/map/devices` | Устройства и их состояние |
| `GET /api/map/detections` | Детекции с фильтрами (вид, период, bbox/радиус, часы, устройство) |
| `GET /api/map/activity_zones` | Зоны активности (сетка или KDE) по видам |
| `GET /api/map/coverage` | Покрытие наблюдениями: где вообще есть данные |
| `GET /api/map/period_diff` | Сравнение двух периодов |
| `GET /api/map/hotspots` | Горячие точки |
| `GET /api/map/hourly` | Распределение по часам суток (UTC) |
| `GET /api/map/summary` | Сводка для дашборда |
| `GET /api/map/export.csv`, `export.geojson` | Выгрузка |

Ограничения на размер ответа: `MAX_SCAN_LIMIT = 200_000` строк на выборку,
`MAX_EXPORT_ROWS = 100_000`, `MAX_LEAFLET_POINTS = 50_000` — защита от запроса,
который положит карту. При превышении API отвечает с указанием, что сузить фильтр.

## Требования к полевому устройству

Устройство шлёт чанки непрерывно: длина 20–90 с (по умолчанию ожидается 60 с),
перекрытие соседних чанков около 5 с, `seq` растёт монотонно. Рассинхрон часов
допускается до `PHOENIX_MAX_CLOCK_SKEW_PAST_SEC` (120 с) назад и
`PHOENIX_MAX_CLOCK_AHEAD_SEC` (300 с) вперёд. При переполнении очереди ответ
`503` означает «повтори позже», а не «потеряно».

Токен устройства — в заголовке `Authorization: Bearer <token>`.

Детекции на стыке чанков дедуплицируются: если реальное перекрытие отличается от
ожидаемого, на границах возможны дубли или пропуски — при настройке устройства
`--expected-chunk-sec` стоит задавать фактический интервал.
