# Phoenix_Bolotni — Android-приложение конечного пользователя (отдельный проект)

**Это отдельный репозиторий/проект** (Kotlin/Android), не часть репо с моделью, не часть Telegram-бота разметки и не часть серверного распознавателя. Делается своим агентом, в своё время. Это основная пользовательская программа — распознаёт птиц по звуку прямо на телефоне, офлайн, показывает результат человеку.

---

## 0. Зависимости от основного репо (модели)

Забираются как готовые артефакты (файлы) при сборке, **не как общий код**:
- `models/bird_model.onnx` — модель.
- `models/classes.json` — порядок классов, должен совпадать с выходом модели индекс-в-индекс.
- `species/ru_birds_whitelist.json` — русские названия и habitat-теги для UI (для показа человеку, а не только латинских слагов).
- `model_config.json` — **обязательно** константы препроцессинга и параметры многократной проверки (см. Задачу 2): частота дискретизации, размер окна, FFT/hop/mel, порог уверенности, класс шума, параметры голосования по нескольким окнам. Это единый источник истины, общий с серверным проектом — если он меняется в репо модели, здесь тоже нужно обновить бандл и пересобрать приложение.

Механизм синхронизации этих файлов при сборке и при обновлении модели без публикации в Google Play — см. Задачу 6.

## 2. Задачи

### Задача 1 [P0] — Базовая интеграция модели (ONNX Runtime Mobile)
**Файлы:** `app/src/main/assets/{bird_model.onnx, classes.json, ru_birds_whitelist.json, model_config.json}`, `ModelRunner.kt`.

**Что сделать:**
- Подключить `onnxruntime-android` (или мобильно-оптимизированный `onnxruntime-mobile`), загрузка модели из `assets`.
- Реализовать препроцессинг **нативно на Kotlin строго по константам из `model_config.json`** (частота дискретизации, ресемплинг, обрезка/паддинг до нужной длины, лог-мел спектрограмма — FFT/hop/mel-бины должны совпадать один в один с тем, что использовалось при обучении, иначе модель будет давать мусорные предсказания). Не хардкодить эти числа — читать из бандла, чтобы при обновлении `model_config.json` не пришлось руками искать константы по коду.
- Рекомендуется по возможности использовать **квантованную (int8) версию ONNX** для мобильного инференса, если в репо модели она публикуется отдельно от полноразмерной — это задача экспорта в репо модели, здесь только предусмотреть, что бандл может содержать именно такой файл.

**Критерии приёмки:** на тестовом `.wav`-файле (записанном на телефоне через микрофон) приложение выдаёт те же top-3 вида и вероятности (с точностью до погрешности округления), что и референсный `inference.py` из репо модели на том же файле.

### Задача 2 [P0] — Непрерывное прослушивание + многократная проверка (без ложной уверенности)

**Контекст от заказчика:** модель не должна быть самоуверенной по одному короткому окну — нужно делать несколько проверок и выбирать наиболее вероятный устойчивый результат, а не первое, что выдал softmax; также важно не терять звук из-за пауз между записями во время реальной работы.

**Файлы:** `ContinuousListeningService.kt` (Android **Foreground Service**, обязательно для длительной записи в фоне по политике Android), `WindowVoteEngine.kt`.

**Что сделать:**
1. Непрерывный захват аудио с микрофона в кольцевой буфер (без пауз между "сессиями записи" — пока сервис активен, поток не прерывается).
2. Нарезка потока на перекрывающиеся окна (шаг `window_stride_sec` из `model_config.json`, например 2.5 сек при длине окна 5 сек) — та же логика, что описана в серверном проекте, реализуется здесь **нативно и независимо**, но по тем же числовым параметрам из общего `model_config.json`, чтобы поведение приложения и сервера концептуально совпадало.
3. Правило подтверждения детекции: вид считается **подтверждённым** и показывается пользователю только если он появляется как топ-1/выше порога как минимум в `min_agree_windows` из последних `window_count_for_vote` окон (те же параметры из `model_config.json`) — единичный уверенный "выброс" на одном окне не показывается как результат.
4. Опционально (P1) — лёгкий test-time augmentation (небольшой сдвиг границы окна) с усреднением вероятностей перед голосованием, если позволяет производительность телефона.
5. UI должен явно показывать разницу между "похоже на..." (сырое предсказание одного окна, не показывается пользователю вообще или помечается как предварительное) и "точно услышано: ..." (прошло голосование) — не смешивать эти два уровня доверия в интерфейсе. Каждая подтверждённая детекция сразу пишется в локальную офлайн-базу (Задача 7) — независимо от наличия интернета.

**Критерии приёмки:** синтетический тест (заранее записанный набор окон с известным паттерном "один случайный всплеск" и "устойчивое присутствие вида") — приложение подтверждает только второй случай; при непрерывной 10-минутной записи в буфере/логе нет "дыр" по времени длиннее долей секунды между обрабатываемыми окнами.

### Задача 3 [P1] — Разрешения, фоновая работа и приватность

**Что сделать:**
- Runtime-запрос `RECORD_AUDIO` и (если используется геопривязка результатов) `ACCESS_FINE_LOCATION` с понятным объяснением, зачем это нужно, до запроса системного диалога.
- Непрерывная запись в фоне — обязателен **Foreground Service** с постоянным уведомлением (по политике Android иначе система убьёт процесс и это же честно перед пользователем — человек должен видеть, что телефон сейчас слушает).
- Явная кнопка "Пауза/Стоп" прослушивания, доступная в один тап, и явный визуальный индикатор активной записи (не только системная иконка микрофона).
- Экран согласия при первом запуске: что приложение слушает окружение непрерывно, что распознавание идёт полностью на устройстве (по умолчанию ничего никуда не отправляется — см. Задачу 4 про то, что любая отправка данных наружу опциональна и выключена по умолчанию).
- Не хранить полные многочасовые аудиозаписи на устройстве по умолчанию — хранить только: (а) историю подтверждённых детекций (вид, время, короткий локальный аудио-фрагмент самого детектированного окна для прослушивания пользователем — это личный локальный лог самого человека, на его же устройстве, не выгружается никуда автоматически), (б) настраиваемый лимит на объём/срок хранения этого личного лога.

**Критерии приёмки:** приложение проходит стандартный чек-лист приватности (permissions запрашиваются с обоснованием, foreground-уведомление всегда видно во время активной записи, есть быстрый способ остановить запись); без явного действия пользователя никакие данные не покидают устройство.

### Задача 4 [P2] — Опциональная интеграция с серверным проектом и с ботом разметки

**Важно:** это два отдельных, независимых, по умолчанию выключенных переключателя в настройках — не предполагать, что они нужны всем пользователям приложения.

**Что сделать:**
- **Переключатель "Участвовать в сети наблюдений"** (выкл. по умолчанию): если включён — приложение **не полагается на постоянную связь** (в лесу/на местности интернета обычно нет), а работает как офлайн-очередь: все подтверждённые детекции копятся в локальной базе (Задача 7) как обычно, а при первом появлении интернета (Wi-Fi/мобильная сеть) фоново дозагружает на сервер (серверный проект, `POST /ingest`, см. его документацию) накопленную **статистику** — не сырое аудио, в духе того же принципа "только статистика", что и в серверном проекте. Требует отдельного экрана согласия с понятным объяснением, что это публикует данные в общую систему мониторинга.
- **Кнопка "Отправить на экспертную разметку"** на карточке любой детекции (в т.ч. неуверенной/незнакомой): передаёт короткий аудио-фрагмент через системный share-intent в Telegram (в чат с ботом-разметчиком) — пользователь фактически просто "делится" файлом штатным способом Android; работает и без интернета в момент нажатия (Android сам поставит отправку в очередь, когда сеть появится) — приложение не имеет собственной интеграции с API бота, это два независимых проекта, соединённых только через обычный интерфейс шаринга ОС.

**Критерии приёмки:** оба переключателя по умолчанию выключены; включение хотя бы одного не меняет поведение и не требует прав, не относящихся к этой конкретной функции; работоспособность базового локального распознавания и сбора статистики (Задачи 1–2, 7) не зависит от состояния этих переключателей и не требует интернета вообще; отключение сети в середине сессии не приводит к потере накопленной статистики — она просто ждёт следующей возможности синхронизироваться.

### Задача 5 [P1] — UI/UX

**Что сделать:**
- Главный экран: крупный индикатор "слушаю/на паузе", лента "только что подтверждено" (вид, русское название, иконка/фото при наличии, время), тап по записи — открывает детали.
- Экран детали детекции: воспроизведение короткого локального фрагмента, вероятность/степень уверенности (по числу окон-подтверждений, не сырой softmax-процент, чтобы не создавать ложного впечатления точности), кнопка ручной коррекции вида (для личного лога пользователя), кнопка "Отправить на экспертную разметку" (Задача 4).
- Экран истории/дневника наблюдений за день/неделю, с фильтром по виду.
- Список видов из `ru_birds_whitelist.json` с русскими названиями и группировкой по `habitat`, используется везде, где нужно выбрать/показать вид (не показывать пользователю латинские слаги напрямую).
- Тема — светлая/тёмная по системным настройкам, крупные читаемые элементы (приложение может использоваться на улице, на солнце, часто одной рукой).

**Критерии приёмки:** пользователь без объяснений понимает, слушает ли сейчас приложение, что оно только что услышало и с какой степенью уверенности, не открывая никаких дополнительных экранов.

### Задача 6 [P2] — Обновление модели без публикации в сторе

**Что сделать:**
- Простая проверка версии бандла (`bird_model.onnx` + `classes.json` + `ru_birds_whitelist.json` + `model_config.json`, упакованные вместе с номером версии и контрольной суммой) при старте приложения (при наличии интернета, не блокируя офлайн-работу) — сравнение с версией, зашитой в приложение или скачанной ранее.
- Если доступна новая версия — скачивание нового бандла с сервера релизов (любой простой статический HTTPS-хостинг с файлом манифеста версии) и подмена активной модели без переустановки самого приложения.
- Откат на предыдущую версию бандла, если новая не загружается корректно (валидация контрольной суммы перед использованием).

**Критерии приёмки:** подмена бандла на тестовый (с другим набором классов) на лету меняет результаты распознавания и список видов в UI без переустановки APK; при повреждённой закачке приложение продолжает работать на последней рабочей версии.

### Задача 7 [P0] — Локальная база детекций и статистика (полностью офлайн, интернет не нужен)

**Контекст от заказчика:** в лесах и вообще на местности интернета обычно нет — распознавание и сбор статистики должны полноценно работать локально на устройстве, так же как это устроено в серверном проекте (там — своя таблица `detections` и своя аналитика), только здесь это личная копия для одного пользователя/устройства. Сеть — опциональна и используется только когда доступна (Задача 4), а не как обязательное условие работы.

**Файлы:** `local/DetectionsDatabase.kt` (Room/SQLite), `local/StatsAggregator.kt`.

**Что сделать:**
- Локальная таблица `detections` (Room/SQLite) на самом устройстве — по составу полей сознательно зеркалирует таблицу `detections` серверного проекта (`species_slug, confidence, window_start_ts, window_end_ts, lat, lon, created_at`), чтобы при появлении интернета (Задача 4) синхронизация шла без преобразования формата.
- Каждая подтверждённая детекция из Задачи 2 сразу пишется в эту локальную БД — **независимо от наличия сети и независимо от того, включена ли вообще синхронизация с сервером**.
- Простая локальная аналитика прямо на устройстве, без сети — по аналогии с серверными "зонами активности", но в масштабе одного пользователя: сколько раз какой вид услышан за день/неделю/сессию; список/точки наблюдений на карте (если офлайн-тайлы карты не предусмотрены — не блокировать функцию из-за этого, достаточно списка с координатами и временем).
- Хранение статистики — бессрочно (это компактные записи, не аудио, места занимают мало); экспорт локальной статистики в CSV/GeoJSON через системный share-intent — эколог должен суметь увезти результат работы, даже если за весь выезд в поле так и не появился интернет.
- Ни распознавание (Задача 1–2), ни запись в локальную статистику **не должны иметь ни одной точки, блокирующейся на сетевой запрос** — сеть нужна только для опциональных вещей из Задач 4 и 6.

**Критерии приёмки:** приложение в авиарежиме (без Wi-Fi и мобильной сети) весь тест-сеанс продолжает распознавать звук, подтверждать детекции и копить локальную статистику без ошибок; экспорт CSV/GeoJSON корректно формируется полностью офлайн; при последующем появлении сети накопленные за офлайн-период данные доступны для синхронизации (Задача 4) без потерь и без дублей.
