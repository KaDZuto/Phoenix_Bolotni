# Phoenix_Bolotni — план доработок для ИИ-агента (репозиторий модели)

**Репозиторий:** https://github.com/KaDZuto/Phoenix_Bolotni
**Текущее состояние (проверено):** EfficientNet-B0 классификатор голосов птиц по лог-мел-спектрограмме, 16 классов, файлы `prepare_data.py`, `train.py`, `metadata/classes.json`, `models/best.pth` (git-lfs), `models/bird_model.onnx` (git-lfs), `models/export_onnx.ipynb`.
**Заказчик:** программист (не эколог), делает инструмент для экологов. Проект — про мониторинг **российских** птиц, преимущественно околоводных/болотных видов.

**Этот документ — только про репозиторий модели** (обучение, качество, воспроизводимость). Три других направления — это **отдельные проекты, отдельные документы, отдельные агенты/время**, специально разведены, чтобы один агент не держал в голове несочетаемые вещи:
- `TELEGRAM_BOT_TASKS.md` — Telegram-бот сбора и разметки данных экологами.
- `SERVER_TASKS.md` — серверный распознаватель для сети микрофонов + карта активности.
- `ANDROID_APP_TASKS.md` — Android-приложение конечного пользователя.

Все три зависят только от **артефактов** этого репозитория (`species/ru_birds_whitelist.json`, `model_config.json`, `models/*.onnx`, `metadata/classes.json`), а не от общего кода — это зафиксировано в каждом из них отдельно.

## 0. Контекст и жёсткие ограничения (прочитать перед началом работы)

1. **Только фауна России.** Любое расширение списка видов — только из чек-листа птиц России (см. раздел 6). Если данные тянутся из глобальных источников (Xeno-canto и т.п.) — **обязательно фильтровать по стране/региону записи**, а не только по виду (один и тот же вид может быть записан в Африке или Азии — такие клипы всё равно валидны биологически, но если стоит цель отражать именно локальные популяции/диалекты — фильтровать и по региону тоже, вынести это в конфиг, не хардкодить).
2. **Не добавлять виды, отсутствующие в фауне РФ**, даже если они "случайно попались" в датасете при автоматическом скачивании — обязательна валидация против whitelist (задача 2).
3. **Прогноз погоды и "заболоченность водоёмов" — НЕ функция аудио-классификатора.** Модель определяет вид птицы по звуку — и всё. Она физически не может предсказывать погоду. То, что реально можно сделать честно:
   - использовать **обнаруженные виды как биоиндикатор** (некоторые виды строго привязаны к водно-болотным угодьям — это принятая в орнитологии/экологии практика биоиндикации), и на основе истории обнаружений строить отдельный, прозрачный скоринг "вероятность/степень заболоченности территории по составу авифауны за период".
   - для погоды — это отдельный сервис, интегрирующий внешний метео-API (Open-Meteo, Gidromet и т.п.) с координатами точки записи, никакого отношения к нейросети не имеющий.
   - **Веса "вид → индикатор заболоченности" должен провалидировать эколог/орнитолог**, агент не должен сам придумывать экологическую значимость видов — задача агента только построить техническую инфраструктуру (таблицу, конфиг, API), которую эксперт потом заполнит/скорректирует.
4. Ничего не ломать: после каждой задачи — прогонять тесты (задача 8) и не коммитить, если тесты красные.
5. Одна задача = один коммит (или один короткий PR), сообщения коммитов — на русском, в формате `feat: ...`, `fix: ...`, `refactor: ...`, `docs: ...`, `test: ...`.
6. **Новых обучающих данных сейчас нет.** Заказчик пока не эколог и не имеет доступа к полевым записям — их должны собирать сторонние экологи через отдельный проект `TELEGRAM_BOT_TASKS.md`. Внутри этого документа реальный приоритет — Задача 1 (whitelist, нужен и боту для клавиатуры видов, и всем остальным проектам для UI), дальше — по мере поступления реальных записей от бота остальные задачи (аугментации/метрики/расширение видов).
7. **Серверный распознаватель и карта активности, а также Android-приложение конечного пользователя — отдельные, независимые проекты** (`SERVER_TASKS.md`, `ANDROID_APP_TASKS.md`). Они не блокируют и не блокируются задачами этого документа, можно вести параллельно. Оба зависят только от артефактов этого репозитория: `species/ru_birds_whitelist.json` (Задача 1), `model_config.json` и спецификации многократной проверки (Задача 14 ниже), `models/*.onnx` + `metadata/classes.json`.

### Задача 1 [P0] — Whitelist российских видов + валидация данных
**Файлы:** новый `species/ru_birds_whitelist.json`, новый `scripts/validate_dataset.py`

**Что сделать:**
- Создать `species/ru_birds_whitelist.json` — список видов фауны России в формате:
  ```json
  {
    "anas_platyrhynchos": {"ru": "Кряква", "habitat": "wetland"},
    "botaurus_stellaris": {"ru": "Большая выпь", "habitat": "wetland"},
  ```

**Критерии приёмки:** запуск `python scripts/validate_dataset.py --data-dir dataset` на текущих 16 классах не выдаёт предупреждений (все 16 видов есть в whitelist); на папке с "левым" видом — выдаёт предупреждение и не прерывает работу.

### Задача 2 [P0] — Класс «фон / нет птицы» + порог уверенности
**Файлы:** `prepare_data.py`, `train.py`, новый `inference.py`

**Что сделать:**
- Разрешить в `dataset/` служебную папку `_noise` (шум города, ветер, дождь, человеческая речь, другие животные — без целевых птиц). Она обрабатывается как обычный класс наравне с остальными (никакого архитектурного изменения не требуется — softmax уже поддерживает N классов).
- Добавить в README короткую инструкцию, откуда брать фоновые звуки (например, ESC-50, Freesound с фильтром по CC-лицензии, собственные полевые записи "тишины").
- Написать `inference.py` — единая точка предсказания (используется и в оффлайн-тестах, и как референс для Android/ONNX):
  - принимает путь к `.wav`, путь к модели/ONNX, `classes.json`, порог `--conf-threshold` (по умолчанию 0.6);
  - возвращает top-3 с вероятностями;
  - если top-1 — класс `_noise`, или top-1 вероятность ниже порога — возвращает `"unknown/uncertain"`, а не просто "самый похожий вид";
  - логика должна быть переиспользуема из Android-приложения (описать в README, как перенести тот же порог в клиентский код на этапе пост-обработки ONNX-выхода).

**Критерии приёмки:** юнит-тест (см. задачу 8) проверяет, что при синтетическом "белом шуме" на входе `inference.py` не возвращает уверенно конкретный вид птицы, если модель обучена с классом `_noise`.

### Задача 3 [P0] — Сплит без утечки данных (group split по исходной записи)
**Файлы:** `prepare_data.py`

**Что сделать:**
- Сейчас `train_test_split` со `stratify` бьёт по классу, но не учитывает, что несколько `.wav`-клипов могут быть нарезаны из одной длинной исходной записи — из-за этого кусочки одной записи могут попасть и в train, и в val/test, завышая метрики.
- Добавить извлечение `recording_id` из имени файла (по конфигурируемому regex/разделителю, например всё до последнего `_partNN`; если разделителя нет — использовать всё имя файла как id) и **группировать сплит по `recording_id`** (`sklearn.model_selection.GroupShuffleSplit` или `StratifiedGroupKFold` при наличии scikit-learn ≥ 1.1).
- Сохранять `recording_id` в `train.jsonl`/`val.jsonl`/`test.jsonl` для прозрачности.
- Если после группировки для редкого класса не хватает записей на 3 сплита — не падать, а честно предупреждать в консоли и класть такие случаи в отчёт `artifacts/validation_report.json`.

**Критерии приёмки:** после прогонки на текущем датасете ни один `recording_id` не встречается более чем в одном из train/val/test одновременно (проверяется тестом).

### Задача 4 [P1] — Аугментации для устойчивости к полевым условиям
**Файлы:** `train.py` (лучше вынести в новый `audio_utils.py`, задача 5)

**Что сделать, добавить как опциональные (управляются флагами/конфигом) шаги аугментации волны *до* спектрограммы:**
- подмешивание фонового шума из банка шумов (`_noise`-клипы или отдельная папка `noise_bank/`) со случайным SNR (например, 5–20 дБ);
- случайное изменение громкости (gain) в диапазоне, например, ±6 дБ;
- случайный time-shift (циклический сдвиг) в пределах клипа;
- лёгкий питч-шифт (`torchaudio.transforms.PitchShift` или через resample-трюк), в пределах ±1–2 полутонов, с вероятностью применения ~30–50% (чтобы не исказить видоспецифичные частоты чрезмерно);
- (опционально) mixup на уровне лог-мел-спектрограмм между двумя случайными сэмплами одного батча с коэффициентом λ~Beta(0.2,0.2), с мягкими метками (label smoothing / soft targets), — пометить это как экспериментальную опцию, выключенную по умолчанию.
- SpecAugment (time/freq masking), который уже есть, оставить как есть.

**Критерии приёмки:** все новые аугментации включаются флагами в конфиге (по умолчанию частично включены для train, полностью выключены для val/test), обучение не падает, добавлен unit-тест на форму тензора после каждой аугментации.

### Задача 13 [P2, отдельный модуль, не трогает нейросеть] — Каркас биоиндикации (для эколога, не для агента "придумывать экологию")
